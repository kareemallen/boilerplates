# Custom Libraries and Templates

This guide shows how to create your own template library for Boilerplates and how to use it with the CLI.

It covers the current runtime format used by this project: `template.json` manifests, renderable files under `files/`, and library management through the `repo` commands.

> **Note:** Legacy `template.yaml` / `template.yml` manifests are not supported since Boilerplates 0.2.0. If a template directory contains one, loading fails with an error telling you to replace it with `template.json` and move renderable files into `files/`.

## What Boilerplates Expects

Boilerplates discovers templates from configured libraries. A library can be either:

- a **git** library: a repository cloned and synced by `boilerplates repo update`
- a **static** library: a local directory on disk that is used as-is

If you run the CLI in a directory that contains a local `config.yaml`, that file is used as the active config. Otherwise, Boilerplates uses the global config at `~/.config/boilerplates/config.yaml` (created automatically with a default library on first run). Git library checkouts are stored in a `libraries/` directory next to the active config file, for example `~/.config/boilerplates/libraries/<library-name>/`.

## Create Your Own Library

Create a separate repository or local directory that contains one or more module folders. The **folder name** must match a CLI module: `ansible`, `bash`, `compose`, `helm`, `kubernetes`, `packer`, `python`, `static`, `swarm`, or `terraform`. Templates are discovered through these folder names, so a template in `compose/` is served by the `compose` commands.

### Recommended library layout

```text
my-templates/
  compose/
    nginx/
      template.json
      files/
        compose.yaml
        README.md
  terraform/
    vpc/
      template.json
      files/
        main.tf
        variables.tf
```

Each template lives in its own directory and must include:

- `template.json`
- a `files/` directory with the files to render

Template files are rendered recursively from `files/` with Jinja2 using custom delimiters:

- `<< >>` for variables
- `<% %>` for blocks
- `<# #>` for comments

Files whose rendered output is empty (or only `---`) are skipped, so you can make entire files conditional.

## Template Manifest

`template.json` must be a JSON object with a top-level `kind` field and a `metadata` object. Set `kind` to the module the template belongs to (matching its parent folder). A minimal manifest looks like this:

```json
{
  "slug": "nginx",
  "kind": "compose",
  "metadata": {
    "name": "Nginx",
    "description": "Containerized Nginx stack",
    "author": "Your Name",
    "date": "2026-07-14",
    "tags": ["web", "proxy"]
  },
  "variables": [
    {
      "name": "general",
      "title": "General",
      "items": [
        {
          "name": "service_name",
          "type": "str",
          "title": "Service name",
          "default": "nginx"
        },
        {
          "name": "container_port",
          "type": "int",
          "title": "Container port",
          "default": 80
        }
      ]
    }
  ]
}
```

Notes on the manifest fields:

- `slug` is optional. When omitted, the template ID is the directory name. A redundant `-<kind>` suffix in the slug is removed automatically (`nginx-compose` becomes `nginx` for kind `compose`).
- Each variable group requires `name`, `title`, and an `items` array. Groups can also set `description`, `toggle`, and `needs`.
- Each item requires `name`. Supported item fields include `type`, `title`, `description`, `default`, `value`, `required`, `needs`, `extra`, and `config`.
- Supported variable types: `str` (default), `int`, `float`, `bool`, `enum`, `email`, `url`, and `secret`. `enum` variables require options in `config`, and `secret` variables support autogenerated values.
- `metadata.version` is optional, but when present it must be an object (with fields such as `name`, `source_dep_name`, `source_dep_version`, `source_dep_digest`, `upstream_ref`, and `notes`).
- `metadata.draft: true` keeps a template out of discovery until you are ready to use it.

Use `variables` to declare every value that appears in the files under `files/`. If a file references a variable that is not declared in `template.json`, validation fails and lists the missing declarations.

## Create the Files

Inside the template directory, place your renderable files under `files/` and use the custom delimiters in the content.

Example `files/compose.yaml`:

```yaml
services:
  app:
    image: nginx:latest
    container_name: << service_name >>
    ports:
      - "<< container_port >>:80"
```

## Add the Library to Boilerplates

Use the `repo` commands to register the library.

### Git library

```bash
boilerplates repo add my-templates \
  --library-type git \
  --url https://github.com/you/my-templates.git \
  --branch main \
  --directory .
```

`--directory` is the subdirectory of the repository that contains the module folders. It defaults to `library`, so pass `--directory .` when the module folders live at the repository root. `--branch` defaults to `main`.

By default the library is synced immediately after adding (use `--no-sync` to skip). You can re-sync all git libraries later:

```bash
boilerplates repo update
```

Or refresh only one library:

```bash
boilerplates repo update my-templates
```

### Static library

If your templates are already on disk, point Boilerplates at the directory directly:

```bash
boilerplates repo add local-templates \
  --library-type static \
  --path ~/my-templates
```

Static libraries do not need syncing with `repo update`; the path is used in place. Relative paths are resolved against the directory of the active config file.

### View configured libraries

```bash
boilerplates repo list
```

### Remove a library

```bash
boilerplates repo remove my-templates
```

Use `--keep-files` if you want to remove only the config entry and keep the local checkout.

## Use Your Templates

Each module folder maps to a CLI command group of the same name: templates in `compose/` are used with `boilerplates compose ...`, templates in `terraform/` with `boilerplates terraform ...`, and so on. Every module provides the subcommands `list`, `search`, `show`, `validate`, `generate`, and `defaults`.

Common workflow:

```bash
# List templates for a module
boilerplates compose list

# Search templates by ID
boilerplates compose search nginx

# Inspect a template
boilerplates compose show nginx

# Validate a template (works on unregistered directories too)
boilerplates compose validate nginx
boilerplates compose validate --path ./my-templates/compose/nginx

# Generate the template
boilerplates compose generate nginx
```

If the same template ID exists in multiple libraries, `list` and `search` show qualified IDs in the form `<template>.<library>` (for example `nginx.my-templates`). Use that qualified form to pick a specific library's version. For unqualified IDs, libraries are searched in the order they appear in the config file, so earlier entries win.

## Practical Tips

- Keep template IDs unique within a library; duplicates in the same library are an error.
- Run `boilerplates repo update` after pushing changes to a git library.
- Put only renderable content in `files/`; keep metadata in `template.json`.
- Use `metadata.draft: true` while iterating, then remove the flag when the template is ready.
- Run `boilerplates <module> validate --path <template-dir>` after adding or changing variables so you catch missing declarations early — this works before the library is even registered.

## Example Workflow

1. Create a repository or local directory for your templates.
2. Add one module folder per kind, such as `compose/` or `terraform/`.
3. Add one template directory per template, with `template.json` and `files/`.
4. Register the library with `boilerplates repo add`.
5. Run `boilerplates repo update` if the library is git-based (done automatically on add unless `--no-sync` is used).
6. List, inspect, validate, and generate the template with the matching module commands.

That is enough to publish your own reusable templates and use them with Boilerplates.
